## 1. 会话提取方法（可复用）

### 1.1 数据源定位

| 平台 | 存储位置 | 说明 |
|---|---|---|
| OpenCode | `~/.local/share/opencode/opencode.db`（SQLite） | 3 张核心表：`session` / `message` / `part` |
| Codex | `~/.codex/sessions/<year>/<month>/<day>/rollout-*.jsonl` | 事件流式 JSONL，每行一个事件 |
| Claude Code | `~/.claude/transcripts/ses_*.jsonl` | 注意：**OpenCode 会话可能被误判为 Claude**（同名 ID 文件存在两个位置） |

**重要陷阱**：`~/.claude/transcripts/` 下可能存在与 OpenCode 会话同 ID 的 JSONL 文件，finder 类工具会误判平台。判定 OpenCode 会话以 `opencode db`（SQLite）为准——`session_info` / `session_read` 工具直接查询的是 OpenCode 数据库，命中了就是 OpenCode 会话。

### 1.2 OpenCode 提取（SQLite）

```sql
-- session: 会话元信息（title, directory, agent, model, cost, tokens）
SELECT id, title, directory, agent, model, time_created, time_updated FROM session WHERE id = ?;
-- message: 消息元信息（role: user/assistant）
SELECT id, data, time_created FROM message WHERE session_id = ? ORDER BY time_created;
-- part: 消息内容（text/reasoning/tool/patch/step-start/step-finish/compaction）
SELECT message_id, data, time_created FROM part WHERE session_id = ? ORDER BY time_created;
```

part 类型与处理：

| part.type | 内容 | 提取策略 |
|---|---|---|
| `text` | 对话正文 | **全文保留**（用户消息、助手回复的核心） |
| `tool` | 工具调用 | 保留工具名 + 参数摘要（截断 300 字符） |
| `patch` | 文件补丁 | 保留文件名 + diff 摘要（截断 600 字符） |
| `reasoning` | 模型思考 | **不导出**（DeepSeek 的明文思考链；价值见 §3） |
| `step-start` / `step-finish` | 回合标记 | 跳过 |
| `compaction` | 上下文压缩 | 保留摘要，标注 synthetic；**compaction 后产生的空占位消息直接剔除** |

### 1.3 Codex 提取（JSONL）

事件类型：`session_meta`（会话头）、`response_item`（对话内容）、`event_msg`（任务状态）、`compacted`（压缩摘要）、`turn_context`、`world_state`。

`response_item.payload.type` 细分：

| type | 处理 |
|---|---|
| `message` | role=user 全文保留；role=assistant 按 `phase` 分（commentary=过程更新、final=最终回复）；role=developer 跳过（系统提示词） |
| `reasoning` | **思维链——见 §2，多数情况为密文** |
| `custom_tool_call` / `function_call` | 工具调用摘要（注意 Codex 参数字段是 `input` 不是 `arguments`） |
| `custom_tool_call_output` | 输出摘要（输出是 `input_text` 数组，需提取 text 拼接） |

**Codex 特有陷阱**：
- 时间戳在事件**顶层**（`d["timestamp"]`），不在 payload 内
- 用户消息可能被系统注入污染：`<turn_aborted>`（用户中断）、`# AGENTS.md instructions`（上下文注入）需过滤
- `encrypted_content`（思维链密文）直接跳过，无导出价值

### 1.4 提取脚本

`/tmp/opencode/extract_sessions.py`（临时脚本，未入库）。用法：

```bash
python3 extract_sessions.py --opencode <session_id> --out <file.md>
python3 extract_sessions.py --codex <rollout.jsonl> --out <file.md>
```

产物命名遵循 docs 惯例：`YYYY.M.D_会话记录_<主题>.md`。

## 2. Codex 思维链加密取证（重要结论）

### 2.1 现象

- 目标会话 945 条 reasoning 事件：`content`（明文）= 0，`summary` = 0，`encrypted_content` = 945（100% 加密）。
- 其他 Codex 会话同样：43/43、158/158 全加密。**这不是个例，是当前上游的常态。**

### 2.2 密文特征

```
gAAAAABqdpT9-xmdAukIMvjuhApLRupRl6_Lht6gKhvJReqaOZppba1cw6FNZ9nzHTIcGvQgQpxoaF9R7VF3P2yGI-r_nw1RPQWaqDqts9TS6x8aw4tJe1ayQDgj7pzGZ0fwTQIXTDfzWWkc6jqXw3Lr07s7CljbfcHjcFMug4KGAZsVychnNFab_WxWmKJaklzF71vj...
```

- 前缀 `gAAAAAB` = **Fernet token 标准特征**（版本字节 0x80 + 8 字节时间戳 + 16 字节 IV + AES-CBC 密文 + 32 字节 HMAC）。
- 实测：版本字节 0x80，时间戳 1786156285（2026-08-08 02:31:25 UTC，与会话时间吻合），结构完全符合 Fernet。
- 长度分布：min 640B / max 3.2KB / 平均 1.7KB（反推明文长度）。

### 2.3 加密发生在哪一层

取证链路（按证据强度排序）：

1. **上游是 YYBB**：`~/.codex/config.toml` → `base_url = "http://127.0.0.1:15721/v1"`；cc-switch 代理日志 `[Codex] >>> 请求目标: https://yybb.dog/v1/responses (model=gpt-5.6-luna)`；cc-switch 数据库 providers 表确认 provider `f3c80286...` = YYBB，api_format=openai_responses。
2. **cc-switch 只是透传**：代理二进制 strings 中有自己的编码前缀 `ccswitch-anthropic-thinking-v1:`（Anthropic 上游时可逆包装），但本会话密文是标准 Fernet，**不是** cc-switch 的包装——加密在更上游（YYBB 服务端）。
3. **本机无密钥**：GNOME Keyring 仅 Chrome/RDP 条目；`~/.codex` 无 `.age` secrets 文件；Codex 客户端源码（`event_mapping.rs`）只提取 `content`/`summary`，对 `encrypted_content` 只保存回传、不尝试解密。
4. **机制确认**：`include: ["reasoning.encrypted_content"]` 的设计意图是让客户端在**下一轮请求中原样回传密文**，由服务端解密保持多轮上下文（cc-switch 源码注释明确此语义）。客户端从设计上就不可读。

### 2.4 结论与出路

**结论：本地无法解密。** 密钥在 YYBB（或其上游）服务端，Fernet 是对称加密，无密钥无解。

**未来可获取明文的路径**：
1. 换走**明文 reasoning** 的上游（如 DeepSeek 官方 responses API），rollout 里会直接有 `content` 字段；
2. 若上游支持关闭加密/明文模式，配置后新会话可读；
3. cc-switch 的 Anthropic 转换路径（`ccswitch-anthropic-thinking-v1:` 前缀）理论可逆，但需要上游走 Anthropic 协议。

## 3. 跨模型思维对比（DeepSeek vs Luna）

> 视角说明：`docs/2026.8.8_OpenCode与Codex能力对比实验.md` 从受控实验（同模型 10 题、reasoning effort 档位、上下文噪音）归因了两平台差异；本节是从真实会话明文侧面的行为观察，两者互补——实验证明"模型不降智、差异在环境"，本节描述"实际行为风格差异"。

### 3.1 数据来源与边界

- **我（DeepSeek）**：OpenCode 会话 reasoning **明文** 311 条（磁盘层实施会话），平均 3.1KB/条，p50=1.8KB，最长 30KB；语言 99% 中英混合。
- **Luna**：reasoning **加密**（~1.7KB/条估算），明文侧面只有 commentary 144 条（平均 157 字）+ 25 条 final + 580 工具调用。
- **归因边界**：Luna 的思维链实际文字读不到，其思维特征是从行为轨迹（commentary 措辞、工具节奏、验证密度）做的**证据性推断**，不是直接引用。

### 3.2 可验证差异

| 维度 | DeepSeek | Luna |
|---|---|---|
| 思考→行动节奏 | 每个 thinking 块后跟 **3.8** 个工具调用（批量执行） | 每个 thinking 块后跟 **1.8** 个工具调用（小步快跑） |
| 思考组织 | 结构化清单式："1. Read docs 2. Check git 3. Cleanup…" | 意图声明式："我先检查…再切换；如果…我会…" |
| 思考内容取向 | 契约解析（"main.rs 说禁止改，但 stage 5 需要 --selftest，冲突"）、全量枚举代码库状态 | 证伪导向（"证据只证明 A 被检测，还不能推出 B 不可行"）、边界划清（"编译层结论不是真机结论"）、多假设并行持有 |

### 3.3 定性结论

- **DeepSeek = 规划型（工程蓝图）**：先建全量心智模型（结构/边界/依赖），按清单推进。优势是大局观与实现密度；风险是计划完成即过早满足、执行阶段思考密度不足（对应复盘里"12 分钟 5 个错误码"的教训）。
- **Luna = 侦查型（侦探笔记本）**：把任务当待证伪假设，每步只接受可验证证据，不把局部失败推广成路线失败（8 月 8 日突破的核心机制）。代价是同样工作量需要更多轮往返。

## 3. 第一部分：8 月 7 日为什么走到归档

### 3.1 直接原因：用户的理性止损

归档决策有明确的原始现场（21:58），是**你的主动决策**，不是 agent 的失败声明。触发点是管理员权限下游戏崩溃（Guerrilla 报告），叠加前几小时连续不断的错误码爬坡（1314、0x522、1326、NoFreeDriveLetter、0xC0000509）。

**一个被掩盖的未决问题**：归档时"管理员权限启动游戏崩溃"**没有完成取证**——对比实验（普通权限 vs 管理员权限启动同一 exe）还没来得及做，你就放弃了。后来复盘确认"手动能跑"，说明游戏本身没问题，权限差异是疑点而非定论。归档决策本身合理（需求可用 BAT 满足、复杂度确实失控），但这条未决线索没有被标注，导致归档说明把它写成了路线失败的证据之一。

### 3.2 "越陷越深"的三个可验证机制

**机制 A：复杂度阶梯 + 补丁堆叠**

- 8.5 小时 27 个提交，其中 1 小时连续 8 个 `fix(disk)`，每个只修一个真实错误码；
- 12 分钟 5 个问题（1326 → 1314 → NoFreeDriveLetter → 已挂载复用 → 游戏崩溃）；
- 关键性质：**每一步修复都是真有效的**（错误码真实、验证真实）。不是幻觉堆叠，而是任务本身的分层复杂度——SMB → 差分盘 → attach → 盘符 → 提权 → 游戏权限，每层都是 Windows 环境的真实坑。
- "越陷越深"的体感来源：**每次测试都部分成功，永远差最后一公里**。修复没有失败，是成功太贵。

**机制 B：验收标准未前置**

- 直到 21:54 才发现"手动能跑 vs 管理员崩"这个决定性差异——这个对比实验如果提前数小时做，路线判断可能完全不同；
- 早期以"游戏启动了"为成功标准，无法区分"真的好了"和"看起来好了"，每个部分成功都鼓励继续加补丁；
- 这不是推理坏了，是验收标准设计缺陷——脱困指南把它沉淀为"把'游戏启动'降级为中间现象"。

**机制 C：归纳过强**

- 终局文档断言"自研 CreateRemoteThread 注入路线对真实游戏**机制性失败**"——stub 三轮取证本身扎实（299 → Sleep → 主动退出），但结论范围被扩大；
- Early-Bird（APC 注入）是**不同机制**，归档前 POC 已出现过成功迹象（`CHILD_INJECTED pid=18004`、`REG_REWRITE`）；
- "某一次注入失败"被推广成"整个注入路线不可行"——这是本次 saga 最值得修正的归纳错误，也是 8 月 8 日突破的裂缝所在。

### 3.3 上下文污染的证据评估（证伪为主）

| 假设 | 证据 | 结论 |
|---|---|---|
| 会话过长导致丢失关键细节 | 1038 条消息、经历 compaction；13:47 出现"前面改过一次但没改到这里"（445 行改漏） | 有损耗痕迹，但不构成主因 |
| 旧结论覆盖新事实 | 未发现"重复犯同一个错"或"把已推翻结论当新发现" | 不支持 |
| 补丁有效性受污染影响 | 每步修复都通过验证（错误码、测试、编译全绿） | 不支持 |

结论：上下文损耗是**叠加因素**（放大了复杂度感），不是**驱动因素**。驱动因素是 3.2 的三个机制。

## 4. 第二部分：8 月 8 日 Luna 为什么能突破

### 4.1 四个可验证的行为差异

**差异 1：第一个推理节点就拒绝过度归纳（最关键）**

Luna 的第一条工作消息（你一句话之后）：

> "目前证据只证明'当前这套 CREATE_SUSPENDED + CreateRemoteThread + LoadLibraryW 被 HZD 识别'，还不能直接推出'所有启动期注入都不可行'。我会把调查拆成：复现现有链路、审查目标进程看到的检测面、设计低可见性的替代注入点……"

它把"机制性失败"当**待证伪假设**，划清证据边界（只覆盖 CreateRemoteThread，未测 APC/loader 自举/静态预加载/手工映射），然后才动手。与 3.2 机制 C 形成镜像对照：同一个事实，一个推广成"路线已死"，一个缩小成"一种方式被检测"。

**差异 2：自主搭建测试环境（把用户环节压缩到最小）**

你说"我就不介入"，Luna 真的没有让你介入：无 Wine 的 Linux 上装 Wine + smbclient + CIFS，处理残留 apt 进程、askpass 传 sudo 密码、qemu-nbd 挂载 115GB VHD 差分（qcow2 backing file 绕过 VHD 不支持 backing 的限制）、NTFS 挂载、定位 exe。8 月 7 日 DeepSeek 侧，测试完全依赖你手动（"贴输出"循环），互动密度因此爆炸。Luna 把"需要用户做的事"压缩到：一个下载包 + 几条真机命令。

**差异 3：每步验证 + 诚实边界**

113/114 项测试、x64/x86 交叉编译、PE 导入校验、`FlushInstructionCache`、静态审查出 `VirtualFreeEx` 竞态并修正。同时反复声明：**"这不是整条功能已恢复：管理员启动崩溃和子进程递归注入是另外两道门"**。它从未把"可编译"当"已成功"。反观 8 月 7 日，恰恰是这些未分离的门（管理员崩溃未取证）被当成了归档依据。

**差异 4：站在 DeepSeek 的资产上做增量**

归档分支里有 24 个提交的完整实现：真机验证过的 disk.rs、1076 行 reg.c、rules/inject/hive 骨架、完整文档。Luna 不是从零突破，是**在 DeepSeek 的失败教训和半成品上做增量**——没有"CreateRemoteThread 被检测"的扎实取证，就没有"early-bird 值得一试"的判断依据。DeepSeek 的失败是 Luna 成功的必要前提。

### 4.2 结构性因素：互动模式

| 维度 | 8 月 7 日 | 8 月 8 日 |
|---|---|---|
| 你的授权 | 全程参与排错（贴输出、跑测试） | "我就不介入"，只给资源（地址/凭据/真机反馈） |
| 互动内容 | 测试-修复循环（用户在循环内） | 推进-确认节奏（用户在循环外） |
| agent 环境负担 | Linux 无法测 Windows 功能 → 全压给用户 | Luna 自建 Wine/QEMU 环境 → 用户只做真机终验 |

同样的授权强度下，agent 的能力差异被放大：DeepSeek 会把问题抛回给你，Luna 会自己解决。

### 4.3 "思维链"问题：能证明存在，不能证明内容

Codex rollout 记录 Luna 有 **807 条 reasoning 事件**（与工具调用交织），但内容**加密存储**（`encrypted_content`）——本地不可读。能证明：它有持续的推理过程，且行为轨迹（先划边界、再设计实验、每步验证）与高质量推理一致。不能证明：思维链文本本身"更聪明"；DeepSeek 会话在 OpenCode 环境运行，**无 reasoning 记录**，无法做同构对比。模型能力差异属于推断，行为差异属于事实。

## 6. 沉淀的操作建议（下一次 saga 怎么做）

1. **归档前必须做"结论边界审查"**：失败的结论覆盖了哪些注入模式/环境/权限？哪些没测？把未测项写进归档说明（本次"机制性失败"漏了 early-bird，是唯一被推翻的归档结论）。
2. **未决线索要显式标注**：管理员崩溃的对比实验未做——这类"未取证就归档"的线索应在归档文档中列为 open issue，而不是并入失败原因。
3. **把"需要用户做的事"列为显式工作项**：真机测试包最小化（一个 zip + 几条命令）；用户互动密度是 agent 质量的放大器。
4. **验收标准前置**：先测最基础的不变量（本例：管理员权限下游戏能否启动），再决定是否值得投入复杂机制。
5. **结论文档与代码一样需要版本化与证据标注**：每个"失败结论"必须绑定证据边界（API、模式、环境、错误码）。
6. **跨 agent 交接材料**：包含"被推翻的假设"清单（脱困指南 §7 模板已覆盖），避免后续 agent 默认接受归档结论。
7. **跨会话分析的价值**：单会话复盘只能看到"自己的失败"或"自己的成功"；跨会话对比才能看到镜像关系（同一个事实的两种归纳方向）。建议复杂 saga 归档时同时保留决策现场（会话原始消息），而不是只留结论文档。

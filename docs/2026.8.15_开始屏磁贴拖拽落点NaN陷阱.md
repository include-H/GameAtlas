# 开始屏磁贴拖拽"拿起来却落回原位"——自定义属性 clamp() 的 parseFloat NaN 陷阱

## 现象

开始屏幕（Win8 磁贴布局）编辑态拖拽磁贴：拖拽"拿起来了"（`.start-screen__drag-ghost--wide` 出现，尺寸约 244×119，宽磁贴 2×4 正确），但落点预览与落位全部失效：

- `.start-screen__drop-target`（落点框）**有时**会更新到新位置，但**经常停留在初始坐标**。
- 松手后磁贴的 `data-row`/`data-col` 与拖拽前完全一样——`applyPlacement` 传出的仍是初始落点坐标。
- 指针移动过程中 pointerdown/pointermove/pointerup 事件全部正常收到，ghost 也跟随指针。

## 排错的曲折过程

以下假设都曾看似有理，最终被逐一推翻：

1. **dragState 原地修改不触发响应式**：怀疑 `dragState.value.targetRow = x` 这种原地修改导致预览框/落位读到旧快照。已改为**新对象整体替换**（`setDragTarget` 中 `dragState.value = { ...state, ... }`）——Vue 3 的 ref 对对象做了深层 reactive 包装，原地修改同样触发更新，**替换对象不是根因**（保留它是因为语义更清晰，且让预览与松手落位读同一快照）。
2. **pointer capture 改变事件链**：怀疑 `metroArea.setPointerCapture` 使 pointermove/pointerup 不再到达 window 监听。实测事件链完全正常——capture 只是把事件重定向到 metro 再冒泡，window 监听照常收到。**capture 无碍，保留作增强**（指针拖出 metro/窗口外仍能收到事件）。
3. **目标框被遮挡 / ghost 尺寸错**：`.start-screen-scrim` 在磁贴层之下不遮挡；244×119 正是 4vw 单元（57.6px）下的 2×4 尺寸，排除。
4. **`[CHANGED]` 判断误把 Vue transition class 当坐标变化**：旧实现曾有该问题，已移除；本次症状与它无关。
5. **`grid.parentElement` 取不到列索引**：HEAD 版本用 `grid.parentElement`（实际是 `.start-screen__group-grid-row`，没有 `data-column-index`）导致网格路径永远 `continue`——**这是真 Bug 之一**，但修复后落点依旧冻结，说明另有根因。

## 关键转折：网格几何换算为什么从不生效

`updateDragTarget` 采用"网格几何换算"（读网格 rect + 单元尺寸 + gap 做数学换算，不依赖 DOM 命中）。其中单元尺寸是这样取的：

```ts
const style = getComputedStyle(grid)
const cell = parseFloat(style.getPropertyValue('--start-cell'))
const gap = parseFloat(style.getPropertyValue('--start-gap'))
```

而 `.start-screen` 里的定义是：

```css
--start-cell: clamp(32px, 4vw, 60px);
--start-gap: 5px;
```

**根因：CSS 自定义属性的计算值与普通属性不同。** 自定义属性只是"token 流"，只有在被替换进真实属性（如 width）时才会求值。`getComputedStyle(el).getPropertyValue('--start-cell')` 返回的是**未求值的原始字符串**：

```
"clamp(32px, 4vw, 60px)"
```

`parseFloat("clamp(32px, 4vw, 60px)") === NaN` → `if (!Number.isFinite(cell) || cell <= 0) continue` → **网格路径的每一次命中都直接跳过，落点永远停留在初始坐标**。

- `--start-gap: 5px` 是纯长度，token 串解析得 5，**一直正常**——掩盖了 cell 的 NaN，让代码看起来"逻辑是对的"。
- 该行为是规范设计（w3c/csswg-drafts#2358：自定义属性"only interpreted as a sequence of tokens, it never resolves to a length"，除非用 Houdini `@property` 注册类型），Chrome/Firefox/Safari 一致。

## 为什么"有时会更新到新位置"

`updateDragTarget` 有三条路径：

| 路径 | 是否依赖 `--start-cell` | 结果 |
| --- | --- | --- |
| 网格几何换算（主路径） | 是（NaN） | **永远不更新** |
| 追加区（`.start-screen__group-append`/`-append-col`/`.start-screen__new-column`） | 否（直接用 `dataset.row/col`） | **正常** |
| 最近网格兜底（组间缝隙） | 是（NaN） | 永远不更新 |

所以只有当指针恰好划过组尾追加条/新列按钮时，落点框才会跳一次；绝大多数时间指针在网格内，落点冻结在初始坐标——与"有时更新、经常停留在初始"完全吻合。

## 最终的解决方案

### 根因修复：单元尺寸改从网格实际像素反推（StartScreen.vue）

```ts
// 网格单元换算步长：--start-cell 是 clamp() 表达式，getComputedStyle 只会返回未求值的
// token 串（parseFloat 得 NaN），不能作为单元尺寸来源；组宽随磁贴占用收缩，
// 列数从内联的 --start-group-cols（纯数字）读取，按 像素宽 = cols×cell + (cols-1)×gap 反推。
// gap 取已解析的标准 gap 属性。
const readGridStep = (grid: HTMLElement, rect: DOMRect): number | null => {
  if (rect.width <= 0 || rect.height <= 0) return null
  const computed = getComputedStyle(grid)
  const gapValue = parseFloat(computed.gap)
  const gap = Number.isFinite(gapValue) && gapValue > 0 ? gapValue : 0
  const colsValue = parseFloat(computed.getPropertyValue('--start-group-cols'))
  const cols = Number.isFinite(colsValue) && colsValue > 0 ? colsValue : START_SCREEN_FREE_COLS
  const cell = (rect.width - gap * (cols - 1)) / cols
  if (!Number.isFinite(cell) || cell <= 0) return null
  return cell + gap
}
```

- 组宽按磁贴实际占用收缩（`--start-group-cols` 由 `groupCols()` 计算，上限 12、下限 2），未使用的列不渲染。编辑态组高固定 `START_SCREEN_GROUP_MAX_ROWS`（10 行，1080p 可视高度，即 2 个 4×4 + 1 个 2×4），落点网格就是整组可视范围，无底部追加条；非编辑态组高随内容自动收缩。列数从内联数字 `--start-group-cols` 读取（纯数字 token，parseFloat 可得；与 `--start-cell` 的 clamp() token 流不同），所以 `rect.width = cols×cell + (cols-1)×gap` 依然精确，反推的 cell 与渲染尺寸一致（含 `clamp()` 已求值的结果）。
- `gap` 改读标准属性 `getComputedStyle(grid).gap`（已解析为 "5px"），不再依赖自定义属性解析。
- 网格主路径与最近网格兜底路径统一使用 `readGridStep`。

### 保留的既有修复（验证有效）

- `grid.closest('.start-screen__group')` 替代 `grid.parentElement`——HEAD 版本取不到 `data-column-index`，网格路径永远 continue（见假设 5）。
- `setDragTarget` 新对象替换 dragState（语义更清晰，见假设 1）。
- metroArea pointer capture 保留为增强（见假设 2）。
- 空位直落 / 冲突链式顶开 / 组底溢出下一组：由 `planStartScreenInsertion`（start-screen-layout.ts）承担，本次未改动其语义。

## 经验教训

1. **自定义属性不能当普通属性读**：`getComputedStyle().getPropertyValue('--var')` 返回未求值的 token 流——`clamp()`/`calc()`/`min()`/`max()` 一律解析失败。需要像素值时，优先从真实属性的已解析值（如 `gap`、`width`）或元素实际 rect 反推。
2. **纯长度掩盖 NaN 陷阱**：`--start-gap: 5px` 恰好能被 parseFloat 解析，让"读自定义属性"这个错误模式显得一直正常；真正坏掉的 cell 被 `continue` 静默吞掉，落点"冻结但不报错"——这种静默失效比抛错难查得多。
3. **"有时生效"是路径分叉的信号**：同一函数三分支，只有不读自定义属性的分支偶尔生效，立刻暴露了"几何换算分支"的问题点。
4. **先验事件链再找状态问题**：pointer capture、事件接收、响应式更新这条链在取证中被证明全通，剩下的可疑面只剩"坐标怎么算的"——把 `--start-cell` 打印出来（`"clamp(32px, 4vw, 60px)"`）即可一眼定案。

## 2. 必须修正的技术点（这是重点）

**a) Registry Overlay 是你文档里最大的认知偏差，但方向对。**

`RegLoadKey` 把 hive 挂到 `HKU\GameVHD`，**不等于**游戏写 `HKCU\Software\Bethesda` 会落到那里。`HKCU` 是绑定到线程令牌（登录会话 profile）的，进程的 `HKCU` 无法通过加载 hive 重定向。真正的读穿透（Game 优先、Host 兜底）只有两条路：用户态 hook（`RegOpenKeyEx/RegSetValueEx`，MinHook/Detours）或内核 `CmRegisterCallback`。

所以 MVP 的正确语义应该是：**seed + 整体替换**——启动时把宿主 `HKCU\Software` 现有内容复制进 GameHive，游戏进程看到的 `HKCU\Software` 就是 GameHive 的全部内容，写入全落 VHDX。代价是运行中看不到宿主新写入的键，但游戏场景几乎没有这个需求。这能让你 Phase 1 完全不碰 hook。你真把它排到 ⭐⭐⭐⭐⭐ 是对的。

另外两个真实坑：32 位游戏走 `HKCU\Software\Wow6432Node` 双视图（GOG 老游戏很多是 32 位）；hive 加载中会锁住 VHDX 卷上的文件，不 `RegUnLoadKey` 就 `DetachVirtualDisk` 会失败——你第 6 节的 Flush Registry → Flush Files → Unmount 顺序恰好正确。

**b) 进程树用 Job Object 而不是手写树。**

`CreateJobObject + AssignProcessToJobObject`，加 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`：job 句柄一关，整个进程树（含孙进程、崩溃弹出的 CrashReporter）全部被杀。你第 8 节要求的"Root + 全部 Child 结束才退出"，Job 基座 + 句柄关闭能免费拿到，比 `Toolhelp32Snapshot` 手写树可靠得多。

**c) 挂载方式建议修正。**

`AttachVirtualDisk` 时用 `ATTACH_VIRTUAL_DISK_FLAG_NO_DRIVE_LETTER`，再 `SetVolumeMountPointW` 挂到宿主空目录（如 `C:\GameVHD-Mounts\Fallout4`）。盘符会撞车（你的 NAS 场景盘符本来就不够用），目录挂载点稳定且可预测。

**d) Junction 两个真实副作用。**

卸载后 junction 指向已卸载卷 = 悬空引用，要维护 junction 状态表，下次挂载时重建；部分启动器（MOD 管理器）会解析并规范化路径，junction 可能被绕开。你 Phase 2 的 hook 方案（`CreateFileW` 等）正是为此存在，路线是对的。

## 3. 先例知识——我认为这里最有价值

- **你这套东西 = WINE WINEPREFIX 的 Windows 原生版**。Lutris/Proton 每游戏一个 prefix（`user.reg` = HKCU hive、`system.reg` = HKLM、`drive_c` = Game 目录），Linux 生态已经用几百万用户验证了这个"一游戏一环境"模型。Windows 原生侧没有对应物，这是真实空白。
- **Cameyo / Turbo.net(Spoon) / BoxedApp** 证明用户态 hook + registry overlay 的应用虚拟化路径可行——你的 Phase 2 就是在复刻它们。
- **Sandboxie** 证明"完全透明"最终需要驱动——这是你的 Phase 3。
- **MojoPac / Hopedot VOS** 我知道的是类别级：便携完整 Windows 环境，商业上失败主要是"虚拟整个系统"太重。**你把范围收窄到单游戏容器，恰好避开了它们失败的部分**——这个判断我认为是成立的。
- **WSL2 / Docker Desktop 用 VHDX 当磁盘**——"一个 VHDX = 一个环境"的现代先例，且你的 NAS 场景 VHDX over SMB 原生支持。

## 4. 诚实边界

- Hopedot VOS 内部实现只有类别级认知，没有细节
- VHDX 字节级格式（日志区/元数据布局）我只懂设计目的，不懂逐字节布局——但正常开发用不上
- windows-rs 当前 API 名要动手时用文档核对，不凭记忆写

**结论**：这份设计在认知上站得住，难点排序我认同（Registry Overlay 最难完全正确，但 MVP 用 seed+替换能绕开）。MVP 范围（Mount + Junction + Hive + Process）确实能覆盖大多数 GOG 游戏。真要动手，第一个决定就是把 Overlay 语义定为"seed + 替换"而不是"读穿透"——这个决定能省掉 Phase 1 最大的坑。

**首启（无状态）**：挂载 → 记录 C 盘关注区状态 → 脚本自动启动游戏（拿 PID）→ 等进程树全退 → diff 出被写目录 → **把目录移动进 VHD**（`C:\Users\Hao\Documents\Horizon Zero Dawn` → `E:\GameVHD\Save\Documents\Horizon Zero Dawn`）→ 写状态清单到 VHD → 卸载

**二启**：挂载 → 读清单 → 在 C 原位置建 junction 指向 VHD 对应目录 → 启动游戏（写入透明落进 VHD）→ 等退出 → **新出现的写入同样回写并追加清单**（收敛过程）→ 删 junction → 卸载

## 5 个关键机制点

1. **回写 = 移动 + 原位建 junction，顺序不可反**。NTFS 不允许对非空目录建 junction，所以必须先移动原目录再建链接。移动本身天然完成"回写"，这个顺序正好自洽。
2. **记录粒度用目录，不用文件**。游戏二启可能写新文件（新子路径），目录粒度劫持后新文件自动落在 VHD 里，不用每次 diff 到文件级。
3. **junction 残留自检必须做**。游戏崩溃/断电会留下指向已卸载盘符的悬空 junction，下次启动前先读清单逐个清理，删不掉的报错。清单存 VHD 里（`E:\GameVHD\state\redirect.json`），状态跟着 VHD 走。
4. **必须等进程树全退再回写**。CrashReporter 之类子进程会持文件锁，需要等待 + 重试。
5. **游戏 exe 必须由脚本启动**，不能像现在这样手动启动——拿不到 PID 就没法跟踪和等待。所以 VHD 里要有 exe 路径信息。

另外说清楚一个边界：**这轮不碰注册表**。地平线这类 GOG 游戏配置存档基本全在文件里，劫持 Documents/AppData 就覆盖了。遇到写注册表的游戏再上 RegLoadKey。

## 沙箱怎么实时隔离注册表

主流沙箱（Sandboxie、Cameyo、VMware ThinApp）用的都是同一套：**用户态 NTDLL hook + 镜像键（write-copy）**。

**拦截层**：把沙箱 DLL 注入每个进程，hook NTDLL 的原生注册表 API——`NtOpenKey / NtCreateKey / NtSetValueKey / NtQueryValueKey / NtDeleteKey / NtEnumerateKey` 等，游戏进程的所有注册表调用都先经过 hook。

**路径重写**：`HKCU\Software\Bethesda` → 重写成 `\Registry\User\S-1-5-21-...\Sandbox\Software\Bethesda`（沙箱镜像键）。

**读穿透写重定向**（核心语义）：
- **读**：先查镜像键，镜像里没有 → 透明读宿主真实键（游戏"以为"还在读宿主）
- **写**：全部只写镜像键，宿主永远不被碰

文件侧完全对称：读穿透（沙箱目录没有 → 读真实位置），写重定向（写入落在沙箱目录）。这就是"透明"的本质——**读合并、写分离**。

**内核注册表回调（`CmRegisterCallback`）**通常只做 allow/deny 和监控，不承担路径改写（内核侧改路径不被推荐）；Sandboxie 的驱动（SbieDrv.sys）主要管句柄隔离和文件底层，注册表主逻辑还是用户态 hook。这是有原因的：hook 不需要驱动签名、不需要过 DSE、更容易维护。

## Windows 自带一个官方先例

**UAC 注册表虚拟化**：32 位非管理员进程写 `HKLM\Software` 被透明重定向到 `HKCU\Software\Classes\VirtualStore\MACHINE\SOFTWARE`，读时合并。内核级实现，机制就是"写重定向 + 读穿透"——证明这个模型是 Windows 认可的正统。但它只覆盖 HKLM + 32 位 + 非管理员，不可控，我们没法借力，只能自己做。

## 工程判断：我们该走哪条路

**MVP 维持搬运式，不升级到 hook 实时隔离。** 理由：

1. **复杂度差一个量级**：hook 方案要处理注入所有子进程、32/64 位双 hook DLL、句柄跨进程传递、反注入对抗——Sandboxie 全栈（DLL+驱动+多年打磨）才稳。对"家庭 NAS 单机游戏"场景，运行期间宿主有几 KB 临时注册表数据，退出即清，**实际影响为零**。
2. **游戏不是恶意软件**：hook 方案最大的收益（防恶意写入）我们用不上；反而引入注入兼容性风险（部分游戏/反作弊对 DLL 注入敏感）。

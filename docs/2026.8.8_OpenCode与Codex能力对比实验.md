# OpenCode vs Codex 能力对比实验：同一模型"降智"假设的证伪与归因

> 日期：2026-08-08
> 作者：Sisyphus（实验执行者 + 被测对象之一）
> 关联：`docs/2026.8.8_GameVHD沙箱Saga复盘.md`（8月7日归档 vs 8月8日突破的归因）、`docs/2026.8.8_顽固问题脱困指南.md`
> 范围：验证"deepseek-v4-flash 在 OpenCode 环境存在智力下降"的假设；定位 OpenCode 与 Codex 的真实差异；用受控实验数据归因

## 0. TL;DR（先给结论）

- **"OpenCode 降智"假设被证伪**：同一模型（deepseek-v4-flash）、同一组 10 道推理题、max 推理档位下，无系统提示 / OpenCode 编排提示 / Codex 完成导向提示三个变体的答案**全部正确**，质量无差异。
- **系统提示词不降智，且实际几乎没被执行**：跨会话审计显示编排协议（委派优先、背景代理、Oracle 咨询）执行率 ≈ 0（task 委派 0-4 次 / 数千次工具调用），模型实际运行在"直接执行模式"，与 Codex 行为同构。唯一被执行的协议项是 todo——因为只有它被 hook 强制注入。
- **真实差异在三个可测维度**：reasoning effort 档位（8月7日归档会话 variant=default，Codex 侧 max）；上下文噪音（编排协议占预算 + TODO continuation 每轮打断 + cache read 2.3 亿 tokens）；互动模式（8月7日测试全压给用户 vs 8月8日 Luna 自建环境）。
- **实验副发现**：max 推理档位在长任务批处理下会吃掉输出预算导致截断（20000 预算下 10 题只输出 3 字符），需要足够大的 max_tokens（256k 级别）。

## 1. 背景与动机

现象（详见 Saga 复盘文档）：

- 8月7日：OpenCode + deepseek-v4-flash（variant=default）实施 GameVHD 沙箱，8.5 小时 27 个提交后归档，用户定性"越修越偏"；
- 8月8日：Codex + gpt-5.6-luna 凭一句话在 early-bird 注入上突破并真机 hook 成功；
- 用户观察：同一模型 deepseek-v4-flash 在 Codex 环境（8月5-7日大量会话）输出质量高，怀疑 OpenCode 环境存在"降智"。

待验证假设：
1. OpenCode 的系统提示词（Sisyphus 编排协议）损害推理能力；
2. OpenCode 对同一模型的调用参数（reasoning effort）与 Codex 不同；
3. 模型本身在 OpenCode 环境输出质量更低。

## 3. 跨会话行为审计（系统提示词遵守率）

### 3.1 协议要求 vs 实际执行

系统提示词（Sisyphus Behavior_Instructions）核心要求：

- "YOUR FAILURE MODE: You attempt to do work yourself instead of decomposing and delegating"
- "ALWAYS decompose the task into independent work units. ALWAYS delegate EACH unit"
- "探索必须用 explore/librarian 背景代理并行（run_in_background=true）"
- "复杂问题 MUST 咨询 Oracle"
- "委派 prompt 必须包含 6 部分"

实际执行（从 OpenCode part 表提取工具调用分布）：

| 协议要求 | 8月7日归档会话 | 8月6日会话 | 当前会话 |
|---|---|---|---|
| task 委派 | **4 次** / 3865 parts | **0 次** / 3972 parts | **0 次** / 338 parts |
| background agents | 0 | 0 | 0 |
| Oracle 咨询 | 0 | 0 | 0 |
| todowrite | 17（hook 强制注入驱动） | 11 | 0 |
| 直接工具调用 | bash 418 / edit 159 / read 121 | bash 417 / edit 205 / read 145 | bash 65 / session_search 10 |

### 3.2 审计结论

1. **编排协议执行率 ≈ 0**：模型系统性无视委派/背景代理/Oracle 条款，实际运行在"直接执行模式"，与 Codex 的行为同构；
2. **唯一被执行的是 todo**——因为 opencode 的 hook（SYSTEM DIRECTIVE TODO CONTINUATION）每轮强制注入，模型无法无视；
3. **影响**：编排协议不构成"被遵守后的伤害"，但构成**每轮固定开销的上下文噪音**（协议文本 + hook 指令 + agent-usage-reminder 提示反复出现）；8月7日会话 tokens_cache_read = 229,640,576（2.3 亿）即为海量重复上下文的量化证据。

## 4. 受控实验设计与结果

### 4.1 实验设计

- **题目**：10 道自包含推理题（逻辑 / 贝叶斯 / Go bug 定位 / Go 并发 LRU 生成 / C 代码审查 / 调试归因 / 架构权衡 / C 指针陷阱 / Go 协程泄漏 / 定积分），纯文本，无工具，规避环境工具集差异，隔离"智力"变量；
- **模型**：deepseek-v4-flash（DeepSeek 官方 API，与 8月7日 Codex 侧同一端点）；
- **变体**：

| 变体 | reasoning_effort | 系统提示 | 输出预算 |
|---|---|---|---|
| A1 | max | 无 | 256k |
| A2 | （默认不传） | 无 | 256k |
| A3 | max | OpenCode 编排提示（Sisyphus 协议 10 条） | 256k |
| A4 | max | Codex 完成导向提示（Codex 规范 10 条） | 256k |
| A5 | max | 无 | 20k（预算截断对照组） |

### 4.4 实验副发现

- **max 需要大输出预算**：A5（20k 预算）中 19,997 tokens 全被推理消耗，最终只输出 3 字符——max 档位在长任务批处理下必须给足输出预算（用户提示：约 256k 级别）；
- max 与 default 都会推理（default 样本 reasoning 占 88%），差异是推理深度与预算消耗，不是"有无推理"；
- 系统提示风格影响"想多少"（reasoning tokens 10k-19k 波动），不影响"想得对不对"。

## 5. 结论与归因

### 5.1 证伪清单

| 假设 | 判定 | 证据 |
|---|---|---|
| OpenCode 系统提示词降低模型智力 | **证伪** | 遵守率≈0（不构成执行伤害）；受控实验证明提示风格不影响正确性 |
| 模型在 OpenCode 环境输出质量更低 | **证伪** | 同一模型同一参数下四个变体输出质量一致 |
| Codex 环境让模型"更聪明" | **证伪** | 差异可全部归因于可测环境变量，无需引入能力差异 |

### 5.2 归因清单（真实差异）

| 差异维度 | 量化证据 | 影响 |
|---|---|---|
| **reasoning effort 档位** | 8月7日归档会话 variant=default；Codex 侧 max | 多步复杂任务的归因深度与耐心不同（沙箱排错类任务敏感） |
| **上下文噪音** | 编排协议 + hook 指令 + 提示循环；cache read 2.3 亿 tokens | 稀释注意力、打断思维流（TODO CONTINUATION 每轮注入） |
| **互动模式** | 8月7日"贴输出"循环 vs 8月8日 Luna 自建 Wine/SMB 环境 | 测试闭环在用户 vs 在 agent，决定排错节奏与结论质量 |
| 工具集 | OpenCode 40+ 工具 vs Codex ~10 工具 | 工具定义占系统预算；不直接影响推理 |

### 5.3 对 8月7日失败归因的修正

Saga 复盘文档（§3）把 8月7日失败归因于复杂度阶梯、验收标准、归纳过强。本实验补充一个此前未量化的维度：**该会话运行在 default 推理档位**——与 Codex 侧 max 的直接差异。但这不改变主归因：default 档位能正确完成单步推理（实验 A2 证明），沙箱失败的主因仍是复杂任务下的方法论问题（补丁堆叠、验收标准、过度归纳），档位差异是叠加因素。

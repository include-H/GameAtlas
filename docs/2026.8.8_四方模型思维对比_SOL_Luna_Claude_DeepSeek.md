## 3. 各模型的可验证特征

### SOL MAX（105.8）：实验矩阵系统性
1. 第一句拒绝接受结论，给出崩溃点四分类框架
2. 6 对照组含消融设计（单 hook/全 hook、普通盘/差分盘）——实验科学方法
3. **问题升维**：为什么一定要进程内 hook？——Minifilter/ProjFS/卷级 CoW/Broker

### Claude 4.8：问题解构与反例直觉（本次实测最大增量）
1. **"崩溃 ≠ 注入失败"**——注入可能成功了，崩的是注入后 hook 干的事。把"注入路线"和"hook 实现"解耦——**这是四方中唯一明说这一层的**（Luna 也实际证明了这点：真机日志显示 hook 初始化成功但文件重定向没生效）
2. **"3A 带反篡改 = 主动崩溃是设计行为"**——用带盾目标证明注入路线失败，"等于用带锁的门证明钥匙不好使"（比喻精准）
3. **"注错进程"**——launcher/DRM stub → 真 game.exe 的链式结构，CRT 打进启动器永远碰不到真游戏
4. 策略建议最有操作性：**先用 DRM-free 标题验证，把"注入能力"和"反篡改对抗"拆开**——这个横切建议 SOL 没给

### Luna（97.8）：证伪纪律执行
- 拒绝过度归纳是第一个推理节点就发生；多门并行持有；站在失败资产上增量

### DeepSeek（88.4）：短板确认
- 接受归档结论（归纳过强）；无系统对照组；想到 APC 但搁置——**短板在实验设计系统性与问题升维，不在代码能力**

## 5. 协作分工模式：SOL 设计 × Claude 审查 × DeepSeek 执行

用户提出的模式（实战验证后扩展）：**用户提需求 → SOL MAX 结构化输出设计 → Claude 4.8 盲区审查 → DeepSeek 执行**。

### 为什么可行（实测互补性）

| 环节 | 最强模型（实测） | 证据 |
|---|---|---|
| 需求 → 方案 | SOL（实验矩阵、归因框架、路径枚举） | DXVK 评审抓出 1 致命 + 4 高危错误 |
| 方案 → 盲区审查 | Claude（问题解构、反例直觉、"崩溃≠注入失败"类洞察） | 探针抓出三方未说的盲区 |
| 方案 → 代码 | DeepSeek（全量心智模型、契约解析、批量执行） | 8.7 实现密度（3.8 工具/思考块） |
| 验证 | SOL 对照组 + Claude no-op 二分 | 探针原文 |

### 模式规则（建议）

1. **SOL 输出"决策完备"设计**：方案、模块接口、测试矩阵、验收断言、未闭合门。
2. **Claude 做盲区审查**：专门找"设计里被默认为真的假设"（如"D3D12 天然回退""崩溃=注入失败"）——它最擅长这个。
3. **DeepSeek 执行**：严格按设计落地，不扩 scope；发现设计空白回用户/SOL/Claude 确认。
4. **验收闭环**：对照测试矩阵验收；设计变更走文档版本化。
5. **成本控制**：SOL/Claude 交互消耗订阅额度，一次问清避免来回。

### 风险与边界

- 执行者不盲信设计：DeepSeek 仍有责任指出技术错误（"此 API 不存在""此路径在只读盘"）。
- 不哄人原则贯穿：任何一方设计过度/遗漏约束，执行时直说。
- Claude 探针实测于 2026-08-08 通过 agentrouter.org（需代理 192.168.1.253:7890；DNS 污染，直连不可达）。

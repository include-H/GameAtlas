# 顽固问题脱困指南：从补丁堆叠回到可证伪证据

> 本文来自 GameVHD 沙箱排错复盘。
>
> 这次复盘的一个重要边界是：DLL 注入、子进程注入和注册表 Hook 已在真实 Windows 游戏环境确认；新增的文件重定向目前只完成了 Wine 合成测试，真实 HZD 仍需要看到 `FILE_REWRITE` 日志才能宣布文件沙箱完成。

## 什么时候应该停下来重置排错方式

出现以下任一信号时，不要继续无条件追加补丁：

- 同一个问题在“白屏、闪退、启动成功但状态不对、偶尔成功”之间漂移；
- 修复只改变了症状，没有证明目标行为已经发生；
- 第一次成功、后续失败，或者换构建、换网络、换启动方式结果不同；
- 日志只证明初始化成功，但没有证明真实业务路径命中；
- 测试全绿，真实环境仍然失败；
- 当前 agent 已经积累了多个未经验证的前提，并开始围绕这些前提继续改代码；
- 远端分支、旧日志或归档文档暗示“这条路线已经失败”，但没有对应的最新实验证据。

这些信号通常说明问题不是“再补一个兼容分支”，而是验收标准、环境边界或问题模型出了偏差。

## 第一步：冻结现场

先记录现场，再修改代码：

```bash
git rev-parse HEAD
git branch --show-current
git status --short
git worktree list
```

至少记录以下信息：

- commit、分支、worktree 路径；
- 未提交修改和未跟踪生成物；
- 实际执行的二进制、DLL 和脚本路径；
- 构建时间、文件哈希和目标平台；
- 测试环境：操作系统、权限、CPU/进程位数、GPU、Wine 或真实 Windows；
- 完整启动命令、日志路径和运行时间。

需要让另一个 agent 独立调查时，给它单独 worktree：

```bash
git worktree add -b diagnosis/gamevhd-poc /tmp/GameManager-gamevhd-poc <known-commit>
```

主工作区只保留用户当前状态。独立 worktree 的价值不是“让模型更聪明”，而是避免未提交修改、旧生成物和来回切分支继续污染判断。

## 第二步：把成功拆成可验证的链路

不要用一个宽泛的 marker 代表整条功能链已经成功。以注入和沙箱为例，至少拆成：

```text
VHD 创建/挂载
  -> 目标进程创建
  -> DLL 注入
  -> Hook 初始化
  -> 规则加载
  -> 子进程继续注入
  -> 注册表 API 命中
  -> 文件 API 命中
  -> 源路径重写到目标路径
  -> 宿主路径没有残留写入
```

每一步都要有自己的证据：

| 层次 | 不能作为唯一证据的现象 | 应该保留的证据 |
| --- | --- | --- |
| VHD | 命令返回成功 | attach、卷、盘符和实际可访问路径 |
| 注入 | 游戏窗口出现 | `HOOK_DLL_PRESENT`、进程模块列表、位数匹配 |
| 初始化 | `RULES_LOADED 12` | 初始化返回值、实际安装成功的 Hook |
| 注册表 | DLL 已加载 | `REG_REWRITE`/`REG_READTHROUGH` 的真实路径 |
| 文件系统 | 游戏启动成功 | `FILE_REWRITE` 的 API、源路径、目标路径 |
| 隔离完整性 | GameData 有文件 | 宿主目录没有新增或变更文件 |

例如：

- `HOOK_DLL_PRESENT` 只能证明 DLL 在进程中；
- `RULES_LOADED 12` 只能证明规则表加载；
- `REG_REWRITE` 只能证明注册表重写；
- 在真实游戏日志中看到 `FILE_REWRITE`，并确认宿主源目录没有写入，才足以支持文件沙箱完成。

## 第三步：每个假设都配一个证伪动作

建立一张假设台账，不要只记录“我觉得是什么”：

| 假设 | 可证伪观察 | 结果 | 结论 |
| --- | --- | --- | --- |
| DLL 没有注入 | 模块列表、初始化日志 | DLL 已加载 | 排除注入失败 |
| 所有注册表函数都必须存在 | 单独记录解析失败的 API | 可选 API 缺失但核心 Hook 可用 | 修改不变量 |
| 规则已加载就代表完整隔离 | 监控宿主 C/D 路径 | 宿主仍有游戏配置写入 | 注册表和文件隔离必须分开验收 |
| Wine 崩溃证明 Hook 失败 | 对比真实 Windows GPU 日志 | Wine 使用 virgl，环境不同 | 只能判定 Wine 不适合做最终 HZD 验收 |
| VHD 挂载成功就代表可用 | 实际访问挂载盘和卷信息 | 游戏能从盘启动 | 保留 VHD 路径，继续排查 Hook 层 |

每个新补丁都必须回答：

1. 它要改变哪个可观察结果？
2. 哪条证据会证明它没有解决问题？
3. 如果结果不变，下一步是回滚、缩小范围，还是修改问题模型？

如果回答不了这三个问题，就还没有足够证据修改代码。

## 第四步：审查隐藏的不变量

顽固问题经常不是某一行语法错，而是代码依赖了一个从未验证的不变量。重点检查：

- “DLL 已加载”是否被当成“所有 Hook 已安装”；
- “规则数量正确”是否被当成“所有路径都能重写”；
- “进程启动”是否被当成“游戏状态已隔离”；
- “API 返回成功”是否被当成“资源在预期位置生效”；
- “函数解析失败”是否真的意味着整个功能必须失败；
- “空参数”是否被误判成 Hook、权限或游戏行为问题；
- “旧日志中的失败”是否仍对应当前二进制和当前环境；
- “Wine 中失败”是否被外推为真实 Windows 中失败；
- “远端归档说明”是否被误当成当前代码的事实。

每个不变量都要绑定一个现场值、命令或日志字段。没有证据的不变量只能作为待验证假设。

## 第五步：切断上下文污染

当 agent 已经连续几轮围绕错误前提修改时，开新会话通常比继续解释旧对话更有效。新会话只提供事实摘要：

- 当前 commit 和独立 worktree；
- 最小复现命令；
- 已确认的日志；
- 已排除的假设；
- 明确的验收标准；
- 禁止执行的破坏性操作。

不要把一长串“之前尝试过的所有补丁”直接当作事实。把它们分为：

- 已由证据确认的结果；
- 尚未证伪的假设；
- 仅仅改变了症状的补丁；
- 不再适用于当前环境的历史结论。

模型切换时也要保持同一 commit、同一环境、同一验收标准。否则比较的不是模型，而是不同问题。

## 第六步：区分环境故障和代码故障

先确认测试环境能否回答当前问题：

| 环境 | 适合验证 | 不足以验证 |
| --- | --- | --- |
| 单元测试 | 字符串、规则和边界逻辑 | 真实进程注入、系统 API 行为 |
| 合成测试程序 | C/D 盘路径重写、读写创建删除 | 真实游戏的 API 使用方式 |
| Wine/虚拟 GPU | DLL 加载、部分 Hook 合成链路 | 真实 HZD 的 GPU 初始化和最终可玩性 |
| Windows 真机 | 进程、权限、VHD、注册表和真实游戏路径 | 未覆盖的 API 或未记录的宿主写入 |

环境不匹配时，不要把“无法验证”写成“功能失败”；也不要把合成测试成功写成“真实游戏已完成”。正确写法是明确能力边界和下一项证据。

## 第七步：用最小闭环验证修复

修复后按由小到大的顺序验证：

1. 用合成程序覆盖 C 盘、D 盘、读取、写入、创建和删除；
2. 确认源路径和目标路径都记录在日志中；
3. 检查宿主目录没有新增或变更文件；
4. 再验证真实目标进程的 DLL、位数和子进程注入；
5. 在真实游戏中观察同一组路径级 marker；
6. 退出后检查 hive、差分盘和宿主目录的清理结果；
7. 删除临时诊断日志和无效补丁，保留回归测试与排错文档。

最终根因必须能够解释所有主要症状，而不是只让某一个症状消失。验证矩阵中只要还剩一个已知变体，就不能宣布根因已解决。

## 与 agent 协作的交接模板

可以将下面的内容作为新 agent 的任务开头：

```text
你将在独立 worktree 中工作，不修改主工作区。

当前事实：
- commit：<commit>
- worktree：<path>
- 目标环境：<Windows/Wine/其他>
- 实际启动命令：<command>
- 已确认日志：<markers>
- 已排除假设：<facts>

目标不是让程序“看起来启动成功”，而是证明：
<具体 API> 捕获到 <具体源路径>，重写到 <具体目标路径>，并且宿主路径没有残留写入。

先只做诊断和证据收集，暂不修改代码。请先报告：
1. 当前 git 状态和实际构建产物；
2. 最小复现步骤；
3. 三个可证伪假设及对应命令/日志；
4. 验收矩阵。

没有新的证据时不要叠加补丁。禁止初始化、格式化或删除现有 VHD。
```

## 这次案例的结论

这次脱困的关键不是“某个 agent 想得更久”，而是同时完成了四个改变：

1. 把“游戏启动”降级为中间现象，把“具体 API 命中具体路径”提升为验收目标；
2. 把 VHD、注入、注册表、文件系统和清理拆成独立链路；
3. 用真实日志推翻“注册表 Hook 等于完整沙箱”“Wine 崩溃等于 Hook 失败”等错误前提；
4. 用独立 worktree 保留主工作区状态，减少旧补丁和旧结论对新调查的影响。

至于 DeepSeek 与 Luna 的模型能力差异，目前不能从这些材料直接证明。能确认的是：工作区、环境、验收标准和证据质量发生了变化；这些因素足以解释大部分结果差异。模型能力可能是因素之一，但不能替代对代码和日志的归因。

## 十条速查清单

1. 记录 commit、分支、worktree、`git status` 和产物哈希。
2. 先确认当前二进制和日志不是旧版本。
3. 把“启动成功”拆成注入、初始化、注册表、文件和清理多个验收项。
4. 每个假设都配一个能证伪它的观察。
5. 优先记录源路径、目标路径、API 和进程，而不是只记录成功 marker。
6. 检查可选 API 缺失是否真的应该导致全局失败。
7. 区分合成测试、Wine 测试和真实 Windows 验收边界。
8. 发现症状漂移或第一次成功后失败时，优先查时序和数据是否被替换。
9. 连续两三次补丁只改变症状时，重置上下文并重新建立问题模型。
10. 真实目标没有产生最终路径级证据前，不宣布功能完成。

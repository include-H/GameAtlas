# SN740 频繁硬崩溃排查——APST 深睡唤醒时序问题（Bug 218365）

> **\[⚠️ 历史存档\]**
>
> 本文档完整记录了 2026.8.16 排查 NAS/迷你主机（Gigabyte BRIX GB-BER7(HS)-5700，AMD Ryzen 7 5700U）频繁"无日志硬崩溃"的全过程：现象 → 逐条被推翻的假设 → 真根因 → 修复方案 → 验证矩阵。
>
> 最终根因：WD PC SN740（OEM 盘）在 AMD 平台上的 APST 深睡唤醒时序缺陷（Linux kernel Bug 218365，WD 官方根因分析），叠加多 agent 并发把内存打穿 swap 作为放大器。处理配置请参考本文"修复方案"一节；盘健康检查参考"盘健康证据"。

## 现象

机器 8/14 起开始频繁"硬崩溃"，`last -x` 全部标记 `crash`（非正常关机），表现为：

- **无任何日志**：崩溃瞬间 journal 一条记录都不落盘（无 panic / OOM / MCE / ACPI 错误）。
- **凌晨空闲也崩**：8/16 00:05 用户断开 SSH 后、无任何活动的情况下，03:47 前崩了一次——盘最闲的时候反而崩。
- **白天重载连崩**：8/16 早上 4-5 个 opencode agent 并发（主会话 128 万 token），08:35 compaction 开始后约 9 点崩；opencode.log 在压缩事件处戛然而止。
- **远程感知**：用户描述"vscode 断开然后偶尔重连"——不是彻底断网，而是时断时续（系统在喘气）。
- **盘级铁证**：SMART 显示 **410 次开机中有 292 次不安全关机（71%）**，该盘历史上就是"硬崩专业户"。

## 排错的曲折过程

以下假设都曾看似合理，最终被逐一推翻：

1. **硬盘是 4KN 格式**：`lsblk` 显示 PHY-SEC=512、LOG-SEC=512，是标准 512b 扇区。盘支持 4096 格式（LBA Format 1）但当前未使用。**排除**。
2. **EC 寄存器被写坏**：用户曾用工具读写 EC 寄存器（一读写就休眠）。但 EC 寄存器是易失 RAM，读写自复位、无法持久化；重装系统 + 彻底放电后问题依旧。**排除**。
3. **电源适配器**：用户已换过 3 个适配器，无效。**排除**。
4. **软件 OOM / 内存挤占**：3 天日志中所有 boot 零 OOM 记录；OOM 只会杀进程不会让整机硬复位。**排除**（但内存打穿是放大器，见真根因）。
5. **内核回归**：6.12.94 与 6.12.101 两个内核都崩。**排除**。
6. **过热**：崩溃后温度正常（CPU 34°C / NVMe 50°C / GPU 33°C），且空闲时段也崩。**排除**。
7. **ASPM L1 链路错误**（LKML 上的 SN740 quirk）：实测本机 `LnkCtl: ASPM Disabled`，该链路上 ASPM 已禁用。**排除**。

## 关键转折：两个对照实验与盘配置取证

### 对照实验一：PM983 一个月零崩溃

用户之前装三星 PM983（企业级盘，固件成熟、APST 参数保守），**插上开机一个月没事**；换成 WD SN740 后开始崩。同一台机器、同样的用法，仅换盘就复现/消失——**机器本身完全健康，问题锁定在 SN740**。

### 对照实验二：内存 32G → 16G

用户指出之前是 32G 内存，当前机器只有 16G 单条（Samsung M471A1G43EB1-CTD DDR4 2667）。内存减半使多 agent 并发时更容易打穿 swap。

### 盘配置取证（nvme-cli）

```
APST 配置（feature 0x0c）：
  APSTE: Enabled
  Entry[0-2]: ITPT = 100 ms → ITPS = 3
  Entry[3]:   ITPT = 2000 ms → ITPS = 4
```

盘空闲 **100ms 就掉进 Power State 3**（深睡），2 秒进 PS4。这个 100ms 正是 WD 官方根因分析中明确点名的触发值。

### 盘健康证据（排除盘本体损坏）

```
critical_warning: 0    media_errors: 0    num_err_log_entries: 0
available_spare: 100%  percentage_used: 0%
power_cycles: 410      unsafe_shutdowns: 292（历史硬崩，非盘故障）
```

## 真正的根因：SN740 APST 深睡唤醒时序缺陷（Bug 218365）

Linux kernel Bugzilla **218365**（"Encounter nvme timeout issue with WD SN740, may affect all WD nvme devices"，报告人 AceLan Kao / Canonical，2024-01-11）。WD 官方根因分析：

> 问题由组合因素导致：
> - **Host APST 设置为 100ms 即进入 LPM**（低功耗模式）
> - SN740 固件在 host 未读完所有命令完成（CQ）前进入 LPM
> - SN740 FW 在发送完所有已处理命令的 completion 后、host 更新 CQ HDBL 寄存器**之前**进入 LPM
> - 导致 LPM 退出后 **MSI-X 中断完全不被断言** → 命令完成机制被破坏 → 主机侧大延迟 → nvme timeout

与机器的对应关系：

| Bug 218365 要素 | 本机实测 |
|---|---|
| APST 100ms 进 LPM | ✅ `ITPT=100ms → PS3` |
| AMD 平台（多数报告来源）| ✅ Ryzen 7 5700U |
| 命令完成中断丢失 → 大延迟 | ✅ "vscode 偶发重连" = 系统在 swap/I/O 上喘气 |
| 空闲时触发 | ✅ 凌晨空闲崩（盘最闲 → 深睡 → 唤醒失败）|
| 无日志 | ✅ I/O 冻结 → journald 写不出盘 |

**放大器**：4-5 个 agent 并发 + 主会话膨胀到 128 万 token（opencode.db 已 353MB）→ 16G 内存打穿 → swap 风暴 → 盘在深睡/唤醒之间被频繁打断，把 APST 缺陷从"偶发"放大成"必崩"。

## 修复方案（已全部生效）

1. **禁用 APST**（立即生效）：
   ```bash
   sudo nvme set-feature /dev/nvme0n1 -f 0x0c -v 0
   ```
   验证：`get-feature 0x0c` 返回 `00000000`。

2. **内核参数禁用 APST 延迟容忍**（重启兜底，已写 grub）：
   ```bash
   # /etc/default/grub 的 GRUB_CMDLINE_LINUX_DEFAULT 追加：
   nvme_core.default_ps_max_latency_us=0
   ```
   当前 boot 已热改生效：`/sys/module/nvme_core/parameters/default_ps_max_latency_us` = 0。

3. **降低 swap 压力**（持久化到 `/etc/sysctl.d/99-swap.conf`）：
   ```
   vm.swappiness=10
   vm.vfs_cache_pressure=50
   ```

## 验证矩阵

| 检查项 | 结果 |
|---|---|
| APST 寄存器（0x0c）| `00000000` ✅ |
| 内核参数 `default_ps_max_latency_us` | `0`（热改 + grub 双保险）✅ |
| nvme 错误日志 | 全 0，无 timeout/reset ✅ |
| SMART | 0 坏块、100% 寿命、无警告 ✅ |
| 修复后 boot | 2.5h+ 稳定，零 nvme/I/O 错误 ✅ |
| 盘电源状态 | 停在 PS0 全速态 ✅ |

## 后续建议

- **换盘治本**：换回 PM983（已验证一个月零崩溃）或海力士 BC711（带 DRAM、APST 参数保守）；128G 对纯 agent 用途足够（当前全盘仅用 20G）。
- **agent 并发 ≤3 个**，主会话避免膨胀到百万 token（中途开新会话/主动 compact）。
- **换盘/重装后重配**：grub 内核参数与 sysctl 需在新系统重新应用。
- 若保留 SN740：禁用 APST + 降 swap 压力后观察，重点盯凌晨空闲时段。

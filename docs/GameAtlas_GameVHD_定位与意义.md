# GameAtlas + GameVHD：项目定位与意义

> 状态：认知基准（2026-08-07 对话定稿）
> 本文是"为什么做这个"的唯一权威记录。技术方案见 `docs/GameVHD_Runtime_实施计划.md`；本文不回答"怎么做"，只回答"为什么"。
> 后续任何实施决策若与本文冲突，先回来对齐本文。

## 一句话定位

**NAS 是全部 DRM-Free 游戏资产的唯一存储；VHD 差分盘让"一份游戏文件、N 台电脑零下载游玩"成立；GameVHD Runtime 让差分盘成为完整游戏工作状态的容器，使备份与迁移的粒度收敛为"一个文件"。**

## 1. 资产约束（一切的出发点）

- 家庭环境 N 台 Windows 电脑，**每台只配备 256G 启动盘**——装不下几百 G 的游戏库
- 游戏资产（DRM-Free 版本）统一存放在 NAS
- 结论：**游戏本体不可能也不应该存在于任何一台客户端本地**，NAS 是唯一存储点

## 2. 已跑通的机制：VHD 差分盘

GameAtlas 已实现并实际运行：

- 每个游戏封装为基础 VHDX（几百 G），存放在 NAS，通过 SMB 共享（只读）
- 客户端首次游玩时在本地创建**差分盘**（几 MB~几百 MB 级别），挂载后游戏可玩
- 游戏本体的所有写入落在本地差分盘，基础盘永不被修改

**性能已验证**：2.5G 乃至千兆网络环境下无性能瓶颈；部分开放世界游戏动态加载地图可能短暂丢贴图，但无伤大雅。此流程已跑通，是后续一切的地基。

## 3. 核心痛点：游戏状态散落、不可知、不可迁

差分盘解决了"游戏本体"的共享，但游戏**状态**（存档、配置、注册表）由游戏进程直接写入宿主 C 盘（Documents、AppData、Saved Games、HKCU），**位置不可预知**：

- A 机玩《地平线》几百小时，A 机崩溃需要重装系统 → **不知道存档在哪里、不知道要备份什么**
- 换 B 机继续玩 → B 机 C 盘没有这份状态 → 游戏状态与游戏本体分离
- 状态损坏/误删 → 无法从 NAS 恢复（NAS 只有本体）

一句话：**本体有 NAS 兜底，状态没有任何兜底。**

## 4. 方案定位：差分盘 = 完整游戏工作状态

目标不是"同步存档"，而是**让差分盘成为完整、自洽的游戏实例**：

```
基础盘（NAS，只读，共享一份） = 游戏本体（几百 G）
差分盘（单台设备本地）        = 本体写覆盖 + 存档 + 配置 + 注册表 = 全部运行状态
```

状态进入差分盘之后：

- **备份** = 把差分盘这一个文件上传回 NAS
- **迁移/恢复** = 目标设备下载该差分盘，挂载同一基础盘 → **回到以前的工作状态**
- **重装系统救赎** = 重装前上传差分盘，重装后下载回来，一切照旧——不再需要"寻找存档"
- **重置** = 删除差分盘 → 回到全新游戏

## 5. 工作状态流转模型

```
                     NAS（唯一资产库）
                   /                  \
      基础盘（只读，共享）      差分盘（状态，按需上传/下载）
              │                        │
              └──────────┬─────────────┘
                         │ 挂载
                    设备 A / B / C
              （同一时刻只有一台设备在玩同一游戏）
```

**关键约束：单写者。** 同一时刻只有一台设备运行同一游戏，因此差分盘的"上传-下载"模型天然成立，不需要冲突合并、不需要版本管理、不需要同步守护进程。这是整个方案成立的前提，必须保持。

## 6. GameVHD Runtime 的角色

差分盘内的写入（游戏本体覆盖）已经天然落盘；缺口是**游戏写宿主 C 盘的状态**绕过差分盘。GameVHD Runtime（纯用户态轻量沙箱）补上这个缺口：

- 游戏进程的文件写入（Documents/AppData/Saved Games）→ 透明重定向进差分盘
- 游戏进程的 HKCU 注册表写入 → 透明重定向进差分盘内的 hive
- 效果：**游戏状态"自动、必然"地归位到差分盘**，不需要人肉搬运，不依赖玩家知道存档在哪

宿主在游戏不运行期间零痕迹（文件、注册表、链接全部清理），差分盘是状态唯一归属。

## 7. 不变量（任何实现不得违反）

1. **单写者**：同一游戏同一时刻仅一台设备运行——差分盘简单迁移模型的前提
2. **状态唯一归属 = 差分盘**：游戏状态不得依赖宿主 C 盘存活
3. **256G 约束**：客户端任何方案不得要求大容量本地存储
4. **性能基线**：现有 VHD 挂载游玩性能（千兆无瓶颈）不得被沙箱显著劣化
5. **GOG/DRM-Free 范围**：反作弊游戏（EAC/BattlEye）不在支持范围；不为其做对抗
6. **基础盘只读**：任何方案不得要求写入 NAS 基础盘

## 8. 决策记录（含被推翻的假设）

| 时间 | 决策/假设 | 结论 |
|------|----------|------|
| 2026-08-07 | "沙箱是否过度工程？是否同步方案（退出时搬状态）更简单？" | **被推翻**。同步方案的状态在宿主与 VHD 间来回搬运，多机场景会互相覆盖错乱；沙箱状态永远只在差分盘，无搬运动作无冲突。在"差分盘=完整实例"的目标下，沙箱是正解 |
| 2026-08-07 | 注册表隔离是否砍掉（用户最初"只关心存档"） | **保留**。注册表内是游戏设置（用户资产），保留 hive 方案使差分盘真正完整、宿主真正零痕迹 |
| 2026-08-07 | Ring0 内核态方案 | **不做**。游戏检测"虚拟机"与我们无关（无虚拟化层）；反作弊检测注入才是真实风险，而反作弊游戏本就不在支持范围。用户态 hook 足够且更干净 |
| 2026-08-07 | 缓存类（shader 等）是否重定向 | **默认重定向**（hook 已拦截，边际成本≈0），可选 `skip_cache_dirs` 开关；真机测试只断言"游戏正常跑 + 存档落 VHD" |

你现在不是在做新功能开发，而是在做“历史包袱审计、语义校正和收口”。

项目背景：
- 这个项目后续大概率不会再新增功能。
- 当前重点不是扩展性，也不是为了“更优雅”继续抽象。
- 当前重点是：清理历史问题、降低理解成本、降低维护成本、消除语义漂移。
- 这是一个已经重写过的项目，因此不要默认“历史兼容写法仍然合理”。
- 如果一个字段、流程、兼容分支已经不是现实需要，应优先删除，而不是保留。

你的工作目标：
- 找出真实存在的语义不一致和结构性问题。
- 优先做低风险、高确定性的整理和删除。
- 保持行为不变，除非我明确要求修正行为。
- 不要为了未来扩展做抽象升级。
- 不要新增抽象层，除非它明确减少历史负担。
- 不要把“以前这么写”当成保留理由。
- 不要把“前端现在这么传”当成兼容理由。

但你必须同时避免误报：
- 不要因为“看起来多一层”“像兼容层”“像旧分叉”“本文件内无引用”就直接判为问题。
- 删除、合并、收口之前，必须先证明该逻辑没有现实边界意义。

## 一、审计顺序

你检查代码时，必须按这个顺序思考：

1. 当前行为先于历史印象
- 先读当前代码、当前调用链、当前测试、当前注释。
- 不允许因为名字像旧逻辑，就默认它还是旧逻辑。
- 不允许因为文件薄、wrapper 很短、helper 本地无调用，就默认它无价值。

2. 先判定状态，再决定是否报问题
每一条候选项只能归入以下四类之一：

A. 真实未处理问题
- 当前代码里仍然存在
- 不是有意保留
- 不是本会话中已处理
- 只有这类才能列入“必须改 / 建议改 / 可以删除”

B. 已处理问题
- 曾经可能是问题
- 但当前代码已经明确收口
- 当前注释、测试、调用链与之匹配
- 不能再按未处理问题重复上报

C. 有意保留项
- 看起来像冗余、兼容或多一层
- 但当前代码里有明确边界意义，或者已有注释说明保留原因
- 这类必须写“可以保留”

D. 信息不足，暂不下结论
- 证据不足，无法判断是真问题、已处理、还是有意保留
- 这类不允许直接建议改代码

3. 只有确认是 A，才进入修改建议或改代码

## 二、问题识别标准

重点检查以下几类：

1. 前后端语义是否一致
- 字段名是否一致
- null / 空字符串 / 空数组 / 缺字段 的语义是否一致
- 默认值、排序、筛选、分页、权限裁剪是否一致
- 前端假设和后端实际返回是否一致
- 前端是否在自己补后端没有承诺的语义
- 能直接使用后端原生语义，就不要在前端发明“等价逻辑”

2. 是否存在语义混用
重点检查是否把下面这些东西混在一起：
- 表单态 和 请求态
- 请求 DTO 和 domain 输入
- transport 兼容逻辑 和 service 业务逻辑
- 后端真实语义 和 前端自行脑补的语义
- 临时 UI 字段 和 持久化字段
- 历史字段名 和 当前真实字段名
- 旧语义名词 和 当前真实语义

3. transport 层是否做了不该做的事情
- handler 是否过厚
- 请求解码、兼容逻辑、响应 DTO、mapper 是否混在一起
- 是否直接把 transport 输入绑定到 domain 模型
- 兼容逻辑如果必须存在，必须明确收口在 decode/adapter 层；否则优先删除

4. service/domain 职责是否清晰
- 参数归一化、校验、权限、业务规则、响应整形分别应该在哪一层
- 是否存在跨层偷渡逻辑
- 是否存在 UI/表单语义泄漏到 service/domain
- domain 层是否被 transport 细节污染

5. 历史兼容写法是否真的还需要
- 不要默认保留兼容
- 不要因为“可能以后有旧调用”就保留
- 如果没有明确现实调用价值，就应优先提出删除
- 但删除前必须先证明“没有现实边界意义”

## 三、反误报硬规则

以下场景默认不能直接报问题，必须先按“可以保留”审查：

1. 权限或上下文决定 payload shape
- 同一路由按权限返回 public/admin 两种 payload
- 如果前端显式做 type guard、fail-fast、admin-only loader
- 这不是“双轨残留”，而是当前接口契约候选
- 若要报问题，必须先证明这两条入口已无边界差异

2. 必要降级
- 如果主动作成功，附属动作失败被明确区分为 warning 或次级错误
- 且不会把“请求失败”和“空数据”混成同一种语义
- 默认判为必要降级候选，不要直接报兼容脏逻辑

3. 模板消费 / 间接消费
- composable 内定义的 helper、本文件内无直接调用，不等于未使用
- 必须检查：
  - 是否被 composable return 出去
  - 是否被 `<script setup>` 解构
  - 是否被 `.vue` 模板引用
- 未完成这条检查前，不允许报“可删除”

4. 薄 wrapper / 薄方法
- 方法很短不代表无意义
- 如果它承担下面任一职责，就不是空壳：
  - 类型收窄
  - fail-fast
  - admin/public 边界隔离
  - route/query -> request 的契约收口
  - transport -> domain 的语义收口
- 若要删除，必须先证明这些职责不存在或已被其他唯一入口完全替代

5. 近期注释和测试
- 如果某条链路已有近期注释说明“为什么保留”
- 或已有测试明确断言当前行为是预期契约
- 你必须优先判断这是“有意保留项”还是“已处理问题”
- 不能跳过这一步直接上报

## 四、删除判定的强制证据

如果你想把某个方法、helper、分支、字段判成“可以删除”，必须同时满足：

1. 当前代码里没有现实调用价值
2. 不承担边界意义
3. 不被模板、组合式返回值、异步注册、路由配置、反射式映射、测试入口间接使用
4. 不被近期注释定义为有意保留
5. 删除后不会留下同一语义链上的旧 fallback、旧方法、旧参数残片

只要有一条不满足，就不能直接判“可以删除”。

## 五、语义链处理纪律

一旦决定处理某条语义链，必须一次性收口，不允许半改半留。

这里的“语义链”指完整闭环，例如：
- 一个列表页的排序 / 分页 / 筛选链
- 一个编辑表单从 UI 到请求 DTO 到 service/domain 的提交链
- 一个查询参数 decode -> service params -> repository query 链
- 一个前端 route/query -> service request -> view state 的查询链

对已决定处理的语义链，必须一次性找出并处理：
- 所有旧入口
- 所有旧参数
- 所有旧 fallback / 兜底
- 所有旧默认值覆盖
- 所有旧命名
- 所有旧分支
- 所有已失效但仍在保护旧语义的测试

如果一次无法完整收口：
- 先不要动代码
- 先输出完整审计结果
- 明确列出这条链上所有需要一起处理的点
- 等我确认后再改

## 六、输出顺序

输出必须按这个顺序：

1. 已处理
- 列出你确认已经收口的项
- 说明你依据什么确认它已经收口
- 如果你之前怀疑过它是问题，必须显式改判

2. 真实未处理问题
- 只列 A 类
- 按严重性排序
- 每条都必须说明：
  - 位置
  - 现状
  - 为什么这是语义债 / 结构债 / 真实 bug
  - 风险或理解成本
  - 建议动作
- 并明确归类：
  - 必须改
  - 建议改
  - 可以删除

3. 有意保留项
- 单独列出
- 必须写清：
  - 保留原因
  - 影响范围
  - 日期
- 不与问题混写

4. 暂不下结论项
- 列出证据不足点
- 说明缺什么证据
- 不给改动建议

## 七、改代码要求

- 默认做小步、可验证的整理
- 但“小步”指：一次选中一条完整语义链，再做最小闭环改动
- 优先做：
  - 删除无价值兼容写法
  - 删除旧方法 / 旧参数 / 旧 fallback / 旧分支
  - request decode / mapper / DTO 分离
  - 注释补齐
  - 命名澄清
  - 删掉前端自行脑补的语义，改成直接使用后端原生语义
- 避免做：
  - 大规模跨层重构
  - 无收益抽象升级
  - 为未来可能需要而保留兼容字段

## 八、注释要求

- 注释要短，只说明“为什么存在”
- 对仍然必须保留的历史逻辑，注明：
  - 保留原因
  - 影响范围
  - 日期
- 不要为已经不需要的兼容逻辑补注释，应该优先删除
- 不要把“表面上像冗余、实际有边界意义”的逻辑误写成“历史兼容”

## 九、执行方式

- 先读代码，再下结论
- 不要凭感觉判断“像没用”
- 不要把“曾经是问题”写成“当前仍然是问题”
- 如果可以直接落地，且能把整条相关语义链一次清干净，就直接改并跑相关测试
- 如果不能一次清干净，就先输出完整审计结果和建议顺序

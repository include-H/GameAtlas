# 游戏库虚拟滚动恢复陷阱与最终解决方案

## 现象

游戏库（GamesView）使用自定义虚拟滚动 + keep-alive 缓存，期望"滚到深处 → 进详情 → 返回"能回到离开的位置。实际表现是一个极其顽固的 Bug，症状随构建版本变化：

- **早期**：返回后白屏，鼠标下滚能看见封面，但"一瞬间像被遮/销毁"——卡片刚出现就被抹掉。
- **中期**：白屏消失（兜底对齐生效），但位置丢失，落回列表顶部。
- **全程**：store 中已加载的游戏数量从 225（10 页）变成 24（第一页）。
- **玄学**：第一次返回偶尔成功（能精确恢复 11708px 位置、39 张卡片在屏），多往返几次必失败；不同构建版本表现不同。

## 排错的曲折过程

我们一度怀疑过多种可能性，每一种都看似有理，最终都被推翻：

1. **keep-alive 生命周期问题**：怀疑组件没被正确停用/激活，导致返回时重挂载。加了 `<transition mode="out-in">`、`<template v-if="Component">`（Vue 官方 RouterView 包裹模式）——**解决了卡顿与"详情页残留库 DOM"问题，但白屏依旧**。
2. **浏览器原生滚动恢复竞态**：怀疑 Chrome 同文档历史导航会按历史条目把 `.content` 滚回旧位置，与我们的 `scrollTo` 打架。加了 `history.scrollRestoration = 'manual'` + 恢复后按容器实际 scrollTop 重新对齐渲染（兜底）——**白屏消失，但位置丢失（用户反馈"进入兜底了"）**。
3. **scrollTo 被夹取**：怀疑恢复时机太早、canvas 高度未就绪，`scrollTo(11708)` 被浏览器夹在矮高度上。改用双 rAF 等待布局落定——**无效**。

## 关键转折：控制台取证

在组件里埋入生命周期日志（`onMounted`/`onActivated`/`onDeactivated` + 恢复结果打印），一次性拿到了决定性证据：

```
[GamesView] onDeactivated {virtualScrollTop: 11572, scrollTop: 0}   ← 离开：位置已保存
[GamesView] onActivated {virtualScrollTop: 11572, refReady: true, scrollTop: 0}  ← 返回：keep-alive 命中！
[GamesView] restore {requested: 11708, actual: 0, scrollHeight: 1468, clientHeight: 1468, ...}
```

- keep-alive **一直工作正常**：组件没被重挂载，`virtualScrollTop` 完整保留（"缓存失效"假设错误）。
- 恢复代码**确实执行了** `scrollTo(11708)`，但 `scrollHeight == clientHeight`（1468px）→ **容器完全不可滚，scrollTo 被夹成 0**。
- canvas 只剩 ~850px ≈ **3 行 = 24 款游戏** → 数据在恢复前就被替换了！

## 真正的根源：`route.query` 的"引用不变量陷阱"

顺着"数据为什么变成 24 款"追查，在 `useGamesView.ts` 找到了真凶：

```ts
watch(() => route.query, () => {
  searchQuery.value = readSingleQueryValue(route.query.search) || ''
  if (route.name !== 'games') {
    return
  }
  void loadGames()   // ← 每次导航都整表重拉第一页
})
```

**Vue Router 每次导航都会重建 `route.query` 对象——即使内容完全相同，引用也必然变化。** 从详情返回 `/games` 时，这个 watcher 必定触发，`loadGames()` → `fetchGames(append: false)` 把已加载 10 页的 store **整表替换成第一页 24 款**。

### 时序竞态解释了所有"玄学"

- **恢复 scrollTo 先跑、fetch 后完成**：一瞬间恢复成功（卡片在屏）→ fetch 完成 → canvas 收缩 → 浏览器把滚动位置强制钳回 0 → 卡片被抹掉 = "像被遮/销毁"。
- **fetch 先完成、恢复后跑**：canvas 已缩 → `scrollTo(11708)` 被夹成 0 = 白屏 / 兜底回顶。
- **网络快慢、过渡时长（out-in 160ms）不同** → 两种时序交替出现 = 第一次成功、后续失败、不同构建表现不同。

"scrollTo 被夹取"只是**症状**；"数据被替换"才是**根源**。

## 最终的解决方案

### 根因修复：内容快照守卫（useGamesView.ts）

```ts
let lastLoadedQueryKey: string | null = null

watch(() => route.query, () => {
  searchQuery.value = readSingleQueryValue(route.query.search) || ''
  if (route.name !== 'games') {
    return
  }
  const queryKey = JSON.stringify(route.query)
  if (queryKey === lastLoadedQueryKey) {
    // keep-alive 恢复：query 内容未变，store 已有该查询的完整数据，跳过重拉
    return
  }
  void loadGames()
})
```

`loadGames()` 开头记录 `lastLoadedQueryKey = JSON.stringify(route.query)`。筛选/排序/搜索**内容**真正变化时快照不同 → 照常重拉；keep-alive 返回（内容相同）→ 跳过，深列表完整保留。

### 辅助修复（消除次要竞态源）

1. **`main.ts`**：`history.scrollRestoration = 'manual'` —— 禁用浏览器同文档历史导航的原生滚动恢复，避免其与应用的恢复逻辑竞争。
2. **`GamesView.vue`**：`onActivated` 中双 rAF（等布局完全落定）再 `scrollTo`，随后按容器**实际** scrollTop 重新对齐渲染——即使被外部因素覆盖，虚拟列表与可视区也永远对齐，最坏退化为回顶、绝不白屏。

## 经验教训

1. **引用变化 ≠ 内容变化**：监听 `route.query`/`route.params` 时，先问"我要的是引用还是内容"。Vue Router 每次导航都重建 query 对象，按引用监听等于"每次导航都触发"。
2. **时序竞态会让同一个 Bug 呈现多种互斥症状**：同一根因，取决于网络与过渡的快慢，可以表现为"成功→被销毁"、"直接白屏"、"兜底回顶"三种样子。看到症状漂移，优先怀疑竞态。
3. **先分清症状层与根源层**："scrollTo 被夹取"是症状，"数据被替换"是根源。控制台取证（生命周期日志 + 拦截 scrollTo + 帧采样）是穿透症状层的唯一可靠手段——猜不如测。
4. **keep-alive 不该背的锅不要背**：这次 keep-alive 全程工作正常，两次都被错误归因。生命周期日志一次就能排除，不要在错误的假设上叠加补丁。

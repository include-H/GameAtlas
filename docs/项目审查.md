## 二、工作原则

### 目标
- 找出真实存在的语义不一致和结构性问题。
- 优先做低风险、高确定性的整理和删除。
- 保持行为不变，除非明确要求修正行为。
- 不要为了未来扩展做抽象升级，不要新增抽象层（除非明确减少历史负担）。

### 审计顺序
1. **当前行为先于历史印象** — 先读当前代码、调用链、测试、注释。不允许因为名字像旧逻辑就默认它还是旧逻辑，不允许因为 wrapper 很短就默认它无价值。
2. **先判定状态，再决定是否报问题** — 每条候选项归入四类之一：
   - **A. 真实未处理问题** — 当前代码里仍然存在，不是有意保留。只有这类才能列入修改建议。
   - **B. 已处理问题** — 当前代码已经明确收口，不能再按未处理问题重复上报。
   - **C. 有意保留项** — 看起来像冗余但有明确边界意义或已有注释说明，写"可以保留"。
   - **D. 信息不足** — 证据不足，不允许直接建议改代码。
3. 只有确认是 A，才进入修改建议或改代码。

## 三、问题识别标准

重点检查：

1. **前后端语义一致性** — 字段名、null/空值语义、默认值、排序/筛选/分页/权限裁剪是否一致。前端是否在自行补后端没有承诺的语义。
2. **语义混用** — 表单态 vs 请求态、请求 DTO vs domain 输入、transport 兼容逻辑 vs service 业务逻辑、临时 UI 字段 vs 持久化字段、历史字段名 vs 当前字段名。
3. **transport 层越权** — handler 是否过厚，请求解码/兼容逻辑/响应 DTO/mapper 是否混在一起，是否直接把 transport 输入绑定到 domain 模型。
4. **service/domain 职责** — 参数归一化/校验/权限/业务规则/响应整形是否在正确层级，是否存在跨层偷渡或 UI 语义泄漏。
5. **历史兼容是否仍需要** — 没有明确现实调用价值的应优先删除，但删除前必须先证明"没有现实边界意义"。

## 四、反误报规则

以下场景不能直接报问题，必须先按"可以保留"审查：

1. **权限或上下文决定 payload shape** — 同一路由按权限返回 public/admin 两种 payload，前端显式做 type guard，这不是"双轨残留"。若要报问题，必须先证明两条入口已无边界差异。
2. **必要降级** — 主动作成功、附属动作失败被区分为 warning 且不混同请求失败和空数据，判为必要降级候选。
3. **模板消费 / 间接消费** — composable 内定义的 helper 本地无直接调用，不等于未使用。必须检查是否被 return 出去、被 `<script setup>` 解构、被模板引用。未完成检查前不允许报"可删除"。
4. **薄 wrapper** — 方法短不代表无意义。如果承担类型收窄、fail-fast、边界隔离、契约收口等职责，就不是空壳。删除前必须证明这些职责不存在或已被完全替代。
5. **近期注释和测试** — 已有注释说明"为什么保留"或测试断言当前行为是预期契约，必须优先判断是"有意保留项"还是"已处理问题"。

### 删除判定的强制证据

判为"可以删除"必须同时满足：
1. 当前代码里没有现实调用价值
2. 不承担边界意义
3. 不被模板、组合式返回值、异步注册、路由配置、测试入口间接使用
4. 不被近期注释定义为有意保留
5. 删除后不会留下同一语义链上的旧 fallback/旧方法/旧参数残片

只要有一条不满足，就不能判"可以删除"。

## 五、语义链处理纪律

一旦决定处理某条语义链，必须一次性收口，不允许半改半留。

"语义链"指完整闭环，例如：列表页的排序/分页/筛选链、编辑表单从 UI 到请求 DTO 到 service/domain 的提交链、查询参数 decode -> service params -> repository query 链。

对已决定处理的语义链，必须一次性找出并处理所有旧入口、旧参数、旧 fallback、旧默认值覆盖、旧命名、旧分支、已失效但仍在保护旧语义的测试。

如果一次无法完整收口：先不要动代码，先输出完整审计结果，明确列出这条链上所有需要一起处理的点，等确认后再改。

## 六、输出与改代码要求

### 输出顺序
1. **已处理** — 列出确认已收口的项及依据，如果之前怀疑过是问题必须显式改判。
2. **真实未处理问题（A 类）** — 按严重性排序，每条说明位置、现状、为什么是问题、风险、建议动作，并归类为"必须改/建议改/可以删除"。
3. **有意保留项** — 单独列出，写清保留原因、影响范围。
4. **暂不下结论项** — 列出证据不足点，不给改动建议。

### 改代码要求
- 优先做：删除无价值兼容写法、删除旧方法/旧参数/旧 fallback、request decode/mapper/DTO 分离、注释补齐、命名澄清。
- 避免做：大规模跨层重构、无收益抽象升级、为未来可能需要而保留兼容字段。
- 注释要短，只说明"为什么存在"。不要为不需要的兼容逻辑补注释，应该删除。

### 执行方式
- 先读代码，再下结论。不要凭感觉判断"像没用"，不要把"曾经是问题"写成"当前仍然是问题"。
- **对比 git 历史再做决定** — 审计发现的每条问题，在报为 A 类之前必须用 `git log` / `git show` 检查近期提交是否已修复或已标注为有意保留。已处理的问题不能重复上报，近期提交中明确注释为有意保留的不能再次提为违规。
- 如果可以直接落地且能把整条语义链一次清干净，就直接改并跑测试。
- 如果不能一次清干净，就先输出完整审计结果和建议顺序。
